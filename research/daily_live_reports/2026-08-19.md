## Fixes Applied

All verified against the live system, not just unit tests. 1,962 tests pass
across `core/tests`, `core/nervous_system`, `signals/meta_context`,

**1. Portfolio state is now published — this is what unblocks the stuck exits.**

The veto was reproduced exactly, against the live store, on the real AMLX exit:

```
EXIT   action = PolicyAction.REJECT   hard_vetoes = ['BROKER_PORTFOLIO_STATE_MISSING']
```

`core/broker_equity_snapshot.py::capture_snapshot` only stages a
`PortfolioState` when it is handed a unit of work, and `capture_from_env` — the
only production caller — never handed it one. Nothing else writes that state, so
`SnapshotBuilder` always resolved `portfolio_state=None`. Postgres being healthy
never mattered; the writer was simply not wired.

`capture_from_env` now opens a `UnitOfWork`, publishes and commits. Publication
failure can never cost the local mark record — a store failure falls back to an
unpublished capture and reports `publication_status`, and the caller now logs an
explicit error when publication does not succeed. After the fix, on the same
intent:

```
EXIT   action = PolicyAction.EXIT     hard_vetoes = []
```

A real portfolio state is already published (10 rows in
`nervous_system.state_records`, 24h validity from 22:36 ET), so **the 09:35 ET
flush on 08-20 can sell AMLX and MRVL260821C00210000 before Friday's expiry**.

**2. A restart now publishes portfolio state at boot.**
`combined_server` gained a startup broker-snapshot thread
(`broker_snapshot_on_start`, default on). The scheduled slots are 16:05/20:05 ET
— both after the 09:35 pre-open flush — so any server started outside them ran
with no portfolio state at all. This makes a crash-restart self-healing, which
is exactly the case that failed here.

**3. The startup readiness check now asks the next-session question.**
`_data_readiness_startup_check` called `readiness_status()`, which asks whether
the stamp is good *right now*. All evening that is true, because
`prev_trading_day` is still today — and then the stamp is stale at the next
open with nothing left to re-check it, since the 22:15 slot has passed.
Confirmed against the live stamp:

```
for_next_session=False -> ok=True   readiness stamp OK (23.7h old)
for_next_session=True  -> ok=False  stamp predates latest completed session (2026-08-19 16:00 ET)
```

Without this fix, a restart tonight would have opened 08-20 on **08-18 bars and
an 08-18 Meta matrix**, with every entry blocked. The check now asks the
next-session question whenever it boots outside 09:30-16:00 ET, so the restart
will launch the readiness catch-up itself.

**4. The pre-open flush now observes a quote before buying an option.**
`governed_submitter._submit` fetches a live two-sided market for option BUYs and
passes it through, with the failure reason carried in `quote_failures` when one
cannot be observed. Exits are untouched — they are deliberately allowed to go
unquoted rather than be trapped. Verified against the live quote API on the
contracts that were refused.

**5. `POLICY_VETO` now names the rules that fired.**
`RoutedRow` carries `policy_vetoes`, and both refusal messages in `live_runner`
append them, so the log reads
`governed path refused sell 36 AMLX: POLICY_VETO (BROKER_PORTFOLIO_STATE_MISSING)`
instead of an unfalsifiable bucket. The same bucket was diagnosed two different
ways on consecutive days; only the second was right.

**6. `_cancel_entry_order` logs.** See Operations And Bugs item 5.

**Regression tests added** (`core/tests/test_broker_equity_snapshot.py`): one
asserting `capture_from_env` publishes *and commits* a state findable by account
alias, one asserting the local record survives an unreachable store. The second
caught a real gap while being written — an exception opening the unit of work
would have lost the snapshot entirely — which is now handled.

### Second pass — daily-loss breaker, nightly catch-up, readiness state

**7. Both hardcoded portfolio limits are now off for paper, mandatory for live.**
`max_daily_loss` and `max_gross_notional` each accept `None`, and the shipped
`MVP_POLICY_CONFIG` sets both that way.

- *Daily loss*: a paper account exists to show a strategy's real drawdown shape,
  and halting it at a dollar figure hides the behaviour the account is there to
  measure.
- *Gross exposure*: on paper the broker's own buying power is the real
  constraint, and it is **already enforced** as
  `BROKER_INSUFFICIENT_BUYING_POWER` (`rules.py:156-157`). A second hardcoded
  ceiling only diverges from the account it is meant to describe — at $150,000
  against a $1,066,016 book it refused every entry outright.

Disabling the gross gate also disables `PORTFOLIO_EXPOSURE_UNKNOWN`, which
exists solely to stop an understated gross from approving a breaching entry.
With no ceiling there is nothing for an uncountable position to endanger, and
leaving it armed would have vetoed entries for a reason that no longer applies.

`PolicyConfig.__post_init__` **refuses to construct** a `PRODUCTION_LIVE` config
with either gate disabled, so turning live on later cannot silently inherit the
paper settings. Per-name sizing is untouched: `max_position_notional` still caps
each order at $5,000. Eight tests cover this, including one asserting that
buying power still binds once the gross gate is off.

**8. A missed nightly is now made up at startup.**
`NightlyScheduler` only ever looks forward, so the 16:45 ET slot missed during
the crash was simply lost. `scripts/nightly_market_data.sh` now writes a
completion stamp (`Data/readiness/nightly_market_data_latest.json`) as its last
step, and the server checks it at boot. The catch-up runs only when **both**
hold: the stamp does not prove a run after the last scheduled slot, **and** the
next session open is within `nightly_catch_up_hours` (default 14). That window
covers any restart from the prior evening through the open while keeping a
mid-session restart from launching a heavy collection. Checked live at 22:57 ET:

```
catch-up needed = True
reason = no completion stamp, missed the 16:45 ET slot, open in 10.5h
```

Six tests cover the decision, one of which caught a real error while being
written: a 06:00 ET restart was measuring against *tomorrow's* open instead of
today's, and would have skipped the catch-up three hours before the bell.

**9. Readiness state is now published — a second entry veto cleared.**
Identical gap to the portfolio one: `adapt_readiness_status` existed, was
tested, and had **zero production callers**. Now published after every readiness
run and at the startup check. `core.live_readiness` remains the authority on
whether entries are authorised; this only records that verdict where the policy
engine can see it. `policy.rule.readiness` now passes.
