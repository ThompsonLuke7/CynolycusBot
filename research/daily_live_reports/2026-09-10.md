**SPY stall.** The seed file named in the config
(`live_meta_matrix_on_trace_ts_live_2026_03_27.parquet`) does not exist. The live
log reads "Cached setup feature frame unavailable", so every 10-minute bar rebuilds
all features over the 50,000-row one-minute buffer.

- **Cost per bar, measured offline:**
  - base frame: 54.6 s
  - setup probabilities: 51.6 s
  - The tree-feature frame alone takes 49.5 s, and it is built twice: once for GA
    probabilities, once for setup probabilities.
  - Total about 106 s.
- **Live is 4–5× slower** (224–348 s per subphase) because inference shares one
  Python process, and its interpreter lock, with the rest of the server. That puts
  a 600 s bar budget over the limit, so the queue grows all session.
- **A shorter incremental window is not parity-safe.** At 40 days, 26/119 base
  columns and 694/2,287 tree columns still differ, and setup probabilities move by
  up to 0.12 (long) and 0.05 (short). Every differing column is a model input:
  the trend-phase columns, `p_pivot_*`, `dist_to_pdh`, and `day_id`.
- **`day_id` is an ordinal session count from the start of the loaded data.** It
  is an input to the entry, exit and setup models. Live computes it over the
  buffer, giving 0–128. Training computed it over the training matrix, which exists
  only as Colab artifacts, so its range is unverified. Any training span longer
  than the buffer gives different values.
- History-length parity test (50k vs 100k vs 200k rows, same end bar): still
  running at append time.

**Options for the SPY stall:**
1. Run SPY inference in its own process: about 106 s per bar, no queue build-up,
   exact parity.
2. Build the tree frame once and share it between the GA and setup paths: saves
   about 50 s per bar, exact by construction.
3. A true incremental feature engine, gated on a decision-level parity test.
4. Settle `day_id` parity: compute it from a fixed training origin, or retrain
   without it.

**Done so far on the SPY path:**
