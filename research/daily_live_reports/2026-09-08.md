## Operations And Bugs

Ranked by severity. **Status lines added 2026-09-09 00:0x ET after the fix
pass**; two items below were reclassified on closer reading and are corrected

1. **`JournalReceipt` AttributeError blocks every Meta Ranker order.**
   [gateway.py:416-417](core/nervous_system/execution/gateway.py#L416) does
   `journal_result.receipts[0].backend.value` /
   `.receipts[0].locator.uri`, but `_write_journal` returns whatever
   `self._journal.write(event)` returns — a bare `JournalReceipt` when the
   journal is a single sink, which has no `.receipts`. The
   [JournalReceipt.is_durable docstring](core/nervous_system/execution/journal.py#L140)
   names this exact hazard ("Callers that pass a bare sink — the Meta path does
   — would otherwise raise AttributeError inside the gateway and never reach the
   broker at all"), so the durability half of the fix landed and the receipt-
   recording half did not. The second call site at
   [gateway.py:661](core/nervous_system/execution/gateway.py#L661) only touches
   `is_durable` and is unaffected. **Cost today: Meta's entire trading day, and
   12 exits queued into tomorrow's open on the same broken path.**

   **FIXED.** `gateway.py` now pulls `(backend, locator)` out of either result
   shape via a `_journal_evidence` helper, and `_journal_failures` does the same
   for the not-durable detail string. Regression test:
   `test_a_bare_single_sink_journal_submits_on_the_durable_path` in
   `core/nervous_system/tests/test_gateway_crash_recovery.py`, verified to
   reproduce the exact production AttributeError against the pre-fix code. The
   pre-existing bare-sink test missed this because it drove a risk-reducing exit
   with Postgres down — the fail-operational path, which only ever reads
   `is_durable` and never records a receipt. 1,254 nervous-system tests pass.

2. **SPY daytrader ran up to 152 minutes behind the tape.** Decision lag from
   `actions.jsonl` (bar timestamp vs recorded_at) grew monotonically: 22.7 min
   at 09:30 ET, 59.0 min by 10:00, 110.8 min by 11:00, peaking at **152.4 min**
   on the 13:20 ET bar, only unwinding after the close. The server logged 39
   `SLOW PHASE inference.on_15m_close for SPY took 325-506s` warnings naming
   this as the cause: "this is what backs the bar queue up; everything
   downstream of it is that far behind the tape". A daytrader acting on
   2.5-hour-old bars is not trading the market it thinks it is.

   **NOT FIXED — instrumented instead, deliberately.** The phase is known; the
   work inside it is not. Two plausible culprits were checked and cleared:
   `_last_processed_ts` does advance, so the agent is not reprocessing history
   each bar, and `predict_row` slices to a single row before predicting, so the
   entry path is not O(frame) despite being handed the whole frame. Past that,
   the next step is a guess — and a speculative change inside the inference path
   is a guess about what the agent decides. So this continues the tactic that
   already worked once: the 2026-09-02 phase timers turned "the loop is slow"
   into "this phase is slow", and sub-phase timers now split
   `inference.on_15m_close` into `base_frame_build`, `swing_setup_probs`,
   `sticky_trend_regime` and `process_rows`, each logging elapsed time and row
   count past the same 5s threshold. Report-only, no behavioural change. Tests
   in `UI/tests/test_slow_phase_timing.py`.

   **It answered immediately.** The server was restarted at 23:28 ET, picked up
   the new timers, and on its first pass logged:

   ```
   23:34:11  SLOW SUBPHASE base_frame_build   took 278.6s over 49951 rows
   23:35:39  SLOW SUBPHASE swing_setup_probs  took  85.4s over  4998 rows
   ```

   364.0s combined, landing squarely inside the 325-506s the phase timer
   recorded across 39 bars during the session. **`base_frame_build` is roughly
   three quarters of the stall**, and it runs over the entire 49,951-row 1-minute
   buffer on every bar.

   Two caveats, stated plainly. This is **one sample, taken on the first pass
   after a restart**, so it may carry warmup cost that steady state does not;
   the close match to the 39 daytime measurements is strong evidence but not
   proof. And no fix is shipped: `_annotate_swing_setup_probs` already caches on
   a `(len, first_ts, last_ts, columns)` key while the base-frame build does
   not, and `_build_base_frame` already contains an incremental
   `_precomputed_base_frame` append path that is inactive here — so the shape of
   the fix is visible, but a cache in the inference path is a change to what the
   agent sees, and it needs a parity test against the uncached frame before it
   goes anywhere near live decisions.

   **Correction to prior work:** a comment in `UI/live_dashboard.py` claimed the
   feature frame build was "measured and ruled out" at 0.87s over the full
   50,000-bar buffer. The measurement above contradicts it by two and a half
   orders of magnitude. That note has been removed from the comment and from
   `UI/tests/test_slow_phase_timing.py` rather than left to misdirect whoever
   picks this up next.

## Orphan Sweep (2026-09-08, user request)

18 unclaimed positions queued for close at the next in-hours server startup, via
`core.startup_queue` (`close_position`, `qty: all`, **paper** account). Largest
first: KLAC $19,050, CIEN260925C00330000 $6,570, BLDP $4,446, ANRO $3,581,
ZG $3,355, Z $3,234, then twelve more between $213 and $1,397.

**The first pass of this scan was wrong, and the way it was wrong matters.** It
returned 25 positions worth $78,422 — eight more than the 17 the 15:57 ET server
log had reported. Seven of those eight were `multi_ticker_swing`'s own live
option book: AZN, CRS, DIA, GPN, NUE, SHOO and SYK, all restored from the broker
at 23:34:58 ET with stop losses set and being actively managed at that moment.
Queuing them would have hand-executed precisely the cross-module liquidation
that item 3 above fixes in code.

They read as unowned because **the swing position book on disk had been
overwritten by this session's own test run.**
`strategies/multi_ticker_swing/tests/test_sibling_module_ownership_guard.py`
drives `sync_from_broker`, which persists as a side effect, and
`position_manager` holds its three state files as module-level *relative* paths
that no test patched. So a green test suite silently replaced the live book with
one synthetic `FIG260724C00022000` row — a contract that expired 2026-07-24 —
and every sibling that reads that file to decide what it may adopt
(`core.orphan_positions.claimed_symbols`) instantly saw seven live positions as
free to take.

Three things were done about it:

1. **The leak is closed.** A new `conftest.py` in the swing test package
   redirects `_OPEN_POSITION_STATE_PATH`, `_DEFERRED_TRAIL_STATE_PATH` and
   `_WORTHLESS_CLOSE_STATE_PATH` into a per-test tmp directory for every test in
   the package. Verified by checksumming the live book across a full 122-test
   run: unchanged, same mtime.
2. **The book was repaired**, reconstructed from the current session's
   `position_opened` audit records — which carry exactly the `to_dict()` payload
   the file stores — restoring all seven positions with their real entry prices
   and stops.
3. **The result was re-derived independently.** With the book repaired, a fresh
   `find_orphans` over a live 220-position broker read returns exactly the 18
   queued symbols, with no manual exclusion list: `scan == queued`.

The queue is a deferral, not an execution: `run_pending` leaves
`close_position` entries pending whenever the market is closed, so a restart
before 09:30 ET will not drain them.
