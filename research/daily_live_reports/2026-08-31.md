## Orphan Root Cause

Added 2026-08-31 after the report was first written, in response to "it feels
like I get more and more orphans each day". **The orphan population is not
growing.** There are three distinct things being conflated.

### 1. Twelve legacy flat-100 positions with lost claims (the whole standing set)

Every one of the 12 is *exactly* 100 shares. That is not a coincidence and it is
not option exercise — it is the signature of a sizing regime the 4H modules used
to run. Reading `order_audit.qty` out of every managed equity leg by entry date:

| Entry date | Equity legs | Sized exactly 100 |
|---|---:|---:|
| 2026-07-17 | 6 | **6** |
| 2026-07-20 | 22 | **22** |
| 2026-07-21 | 20 | **20** |
| 2026-07-22 | 14 | 0 |
| 2026-07-23 onward | every day | 0 |

Flat-100 sizing ran through 2026-07-21 and stopped on 07-22, after which
everything is notional-sized (today: CLYM 363, ELDN 1672, BRUN 298, TECX 164).
All 12 orphans are already present in the earliest broker snapshot we retain
(2026-07-15), so they date from that era or earlier, and their module claims
were subsequently lost. They are a **fixed, historical set** — a cleanup job,
not a leak.

### 2. Auto-exercise of ITM options — a real generator, but already fixed

This is the mechanism that produced TECK and SU (07-24 expiry) and GRAB, U,
SMCI and FIG (08-14 expiry): a long call expiring ITM is auto-exercised into 100
shares per contract, the module drops the *option* as `not_found` and never
claims the *equity*.

It is fixed. `core/live_risk_pass.py` has a calendar-aware
`expiring_before_next_session` flatten with a 15:45 ET cutoff, and
`multi_ticker_swing`'s position manager has its own `expiration_itm_cutoff` at
the same time. Both postdate the 08-14 incident. Proof it works:
MRVL260821C00210000 x4 was flattened on 08-21 with realized P&L logged, and the
08-28 batch fired on time (it could not fill only because the contracts were
already worthless).

### 3. A daily false positive from the SPY daytrader (this is the "growth" illusion)

`core/orphan_positions.py` consults four `managed` state files plus
`multi_ticker_swing`'s book. **The SPY daytrader's book is not among them**, so
its intraday 0DTE contract is reported as an orphan for as long as it is held:

- 08-28: `SPY260828P00771000`
- 08-31: `SPY260831C00767000` — flagged on 3 consecutive scans, 09:54 to 10:05,
  gone once the position closed at 10:08.

This is pure noise, but it is *new noise every single day*, with a different
contract symbol each time, which is almost certainly what creates the impression
that orphans keep accumulating. The fix is to add the SPY daytrader's book to
the detector's claim sources.

## SPY Daytrader Lag: Diagnosis

Added 2026-08-31. Investigation only — **no code changed for this yet.**

### The loop is saturated during RTH, and the broker-poll counter proves it

`UI/live_dashboard.py` runs one thread that does two jobs:

```python
bar = bar_queue.get(timeout=0.5)
if bar is not None:
    processor.handle_bar(bar)
    continue                      # <-- maintenance is skipped whenever a bar is waiting
# broker reconcile / expiring-position maintenance runs ONLY here
if now - last_broker_poll >= cfg.broker_snapshot_interval_sec:  # 30.0s
```

Broker maintenance therefore runs only when the bar queue drains. Counting
`broker-state.jsonl` writes per hour today makes the saturation unmistakable:

| Hours (UTC) | Session | Broker polls/hour |
|---|---|---:|
| 00:00-13:00 | overnight/pre-open | 112-119 (≈ one per 31s, matching the 30s throttle) |
| **14:00-20:00** | **RTH** | **3-6** |
| 21:00-23:00 | post-close | 72, 118, 119 |

During the session the queue essentially never empties, so the loop spends all
its time in `handle_bar` and the deficit accumulates. It clears within minutes
of the close, which is exactly the shape of the observed lag curve.

### It is not queue backpressure

The SPY queue (`intraday_queue`, maxsize 10,000) is symbol-filtered to
`SPY, VIXY, QQQ, IWM, TLT, UUP` — six symbols, ~6 bars/min. It logged no drop
warnings at all. This is a *consumer speed* problem, not a fan-out problem, and
it is a different fault from the intraday-structure drops.

### The likely hot path, and the measurement still needed

On every 10-minute close the loop calls:

```python
action = inference.on_15m_close(df_1m=buffer.to_dataframe(), closed_bar=bar15)
```

`buffer` is a `BarRingBuffer(maxlen=50000)` of 1-minute bars that is **never
reset per session** — it accumulates for the life of the process. Materialising
it and running inference over it on every decision is the obvious candidate for
the per-cycle cost, and it fits the fact that Monday (process day 4, peak lag
153 min) is worse than Friday (process day 1, peak 129 min).

This is a strong hypothesis, **not a confirmed measurement**. The buffer only
holds roughly 2,000 rows by Monday, which is not by itself slow to convert, so
the cost is more likely inside `inference.on_15m_close` than in
`to_dataframe()`. The next step is to time that call directly rather than
guess — add a duration log around it and read one session.

### Candidate fixes, cheapest first

1. **Instrument first.** ✅ **Done 2026-09-01.** The loop now aggregates
   wall-clock for the SPY handler, the context handlers and the maintenance
   block, and logs one line a minute:
   `[live] loop cost over 60s: spy_bars=N mean=…s max=…s | context_bars=N mean=…s | maintenance=N mean=…s max=…s | queue=N busy=…%`
   `busy%` over 100 means the loop is oversubscribed and the lag is accruing.
   Deliberately measurement-only: fixes 2-4 pull in opposite directions
   depending on which bucket dominates, so one session of this data decides.
2. **Skip stale bars at ingest.** A 10-minute daytrader gains nothing from
   processing a 1-minute bar that is two hours old. Dropping bars older than a
   threshold would let the loop stay near real time instead of faithfully
   working through a backlog it can no longer trade on.
3. **Bound the inference window.** If `on_15m_close` is recomputing over the
   whole buffer, pass only the lookback the features actually need.
4. **Move broker maintenance to its own thread** so it is not starved by bar
   traffic. This is a correctness issue in its own right: for six hours a day
   the position/order reconcile that is supposed to run every 30s runs every
   10-20 minutes.
5. A **restart** shrinks the buffer and will reduce the lag, but it does not fix
   it — the deficit still rebuilds within a single session.
