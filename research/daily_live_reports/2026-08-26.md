## Operations And Bugs

1. **A Meta subprocess has been hung for 13 hours holding a Postgres lock —
   self-deadlock in the governed path.** PID 2491837, launched by the 09:35 ET
   pre-open flush, is still alive at 22:45. `pg_stat_activity` shows three
   sessions all opened at 13:35:12-13 UTC:

   | pid | state | since | waiting on |
   |---|---|---|---|
   | 1776791 | `idle in transaction` | 13:35:12 UTC | client — holds an uncommitted `INSERT INTO context_snapshots` |
   | 1776800 | `active` | 13:35:13 UTC | `Lock/transactionid`, **blocked by 1776791** |
   | 1776790 | `idle` | 13:35:12 UTC | client |

   `pg_blocking_pids(1776800) = [1776791]` — one process, two connections,
   deadlocked against itself.

   **Cause.** `build_router` constructs
   `SnapshotBuilder(StateRepository(session_factory()))` with a **single
   long-lived session created once and never committed**
   (`gateway_execution.py:628`). `SnapshotBuilder` calls
   `save_context_snapshot_idempotently` on it
   (`snapshot_builder.py:146`), leaving the inserted row's transaction open.
   The coordinator then opens a **separate** UnitOfWork
   (`unit_of_work_factory=lambda: UnitOfWork(session_factory)`) and
   `_persist_planning -> save_chain` inserts the **same `snapshot_id`**
   (`coordinator.py:359` -> `state.py:676`). `ON CONFLICT DO NOTHING` still has
   to wait on the other transaction's uncommitted unique key, so the second
   session blocks on the first, which will never commit because the process is
   blocked on the second. There is no `lock_timeout` or `statement_timeout`, so
   it waits forever.

   A faulthandler dump of a dry-run (`submit=False`, no broker order)
   reproduces it exactly:
   `route -> _route_one -> process_intent -> _persist_planning -> save_chain ->
   save_context_snapshot_idempotently -> psycopg wait`.

   **Why today.** This path had been unreachable for weeks: every Meta order
   was vetoed at the policy stage before reaching `process_intent`. The
   `is_risk_reducing` fix applied 2026-08-25 23:51 ET let the AMLX trim through
   the veto, and the first order to reach the persist layer hit the deadlock.
   The fix did not create this defect, it exposed it — but **the practical
   effect is that tomorrow's 09:35 flush will hang the same way.**

   **No order was placed.** The broker shows zero orders today for AMLX, PURR,
   TEM or FIGR, and all four positions are unchanged (AMLX 227, PURR 100,
   TEM 100, FIGR 100). Nothing traded on the hung attempt.

   Needs a human: kill PID 2491837 to release the lock, then either fix the
   session lifecycle or hold the policy fix until it is fixed. A `lock_timeout`
   on these writes would have turned a 13-hour silent hang into a fast logged
   failure and should be added regardless.

2. **The 20:05 snapshot re-marked the book +$17,306 above its own 16:05 capture
