## Operations And Bugs

1. **Two silent whole-tree kills; the supervisor cannot survive them.**
   Run 1 launched 00:37:58, last log line 02:55:05. Run 2 launched 09:01:40,
   last log line 11:25:44 (truncated mid-write). In both cases there is no
   `[supervisor] combined_server exited rc=…` line, no restart-ladder entry, no
   OOM, no traceback and no shutdown request — the supervisor died alongside the
   child, so its restart logic was never reached. `who -b` reports the host
   booted 2026-07-30 19:45; combined with the 7/29 death at ~18:53 ET, this is
   the third kill in two days and matches the known recurring WSL2 VM crash
   pattern. **A supervisor that lives inside the thing it supervises cannot
   restart it.** This needs an out-of-VM restart path (Windows Task Scheduler /
   `wsl.exe` invocation, or a systemd unit inside WSL with
   `systemd=true`) before any other bug on this list matters, because every
   other item below is downstream of "nothing was running".

2. **Readiness stamp stale for a third day; both catch-ups were killed
   mid-build.** `Data/readiness/latest_success.json` still reads
   `2026-07-28T02:05:48Z` (2026-07-27 22:05 ET). Run 1 started 02:12:22 ET,
   cleared steps 1–3 by 02:42, entered the 4H feature rebuild at 02:42:27 and
   was killed. Run 2 started 10:37:54 ET, cleared steps 1–3 by 11:08, entered
   the rebuild at 11:08:01 and was killed at 11:17:17 having built 2,875 of
   2,888 tickers — **it was roughly 30 seconds from finishing**. Two
   sub-problems compound this:
   - *The lock wait is a self-deadlock.* Run 1 was launched at 00:38 but did not
     begin until 02:12 (1h34m blocked on `Data/runtime/live_data_jobs.lock`);
     run 2 was launched at 09:01 and began at 10:37 (1h36m). **Root cause
     confirmed by live reproduction at 20:44 ET**: `combined_server` acquires
     this lock in `heavy_job_guard` and *then* launches
     `nightly_data_readiness.sh` as a child, so the script blocks on a lock its
     own parent holds. The script had a parent-detection escape hatch, but it
     sat in the `flock` *timeout* branch — it only ran after burning the full
     90-minute `READINESS_LOCK_WAIT_SECONDS`. Every catch-up therefore started
     ~95 minutes late by construction, which is what made a 30-minute job
     wide enough to be caught by a crash. Fixed the same evening; see
     Follow-Up below.
   - *The job is all-or-nothing.* Losing the last 0.5% of a 30-minute feature
     build discards the 8h35m of work in front of it and leaves the stamp
     exactly as stale as before. A checkpoint, or writing the stamp on
     step-level completion, would have made both of today's runs count.
   - *A stale lock is left behind.* `live_data_jobs.lock` still names
     `pid=22829`, dead since 11:25. The `flock` itself released with the
     process, so this should not block the next run, but the metadata is now
     lying about who holds it.

3. **Momentum's `auto_trade: true` alerts are misleading, though nothing was
   lost.** ULCC, XRAY and FRSH were emitted at 09:44:15 ET carrying
   `auto_trade: true`, and no orders followed. That is correct — the run was
   `--flush-pending-open`, which submits only entries already queued in
   `pending_open_entries.json` (no such file exists), and it duly logged
   `pending-open flush: submitted 0 / skipped 0` and `orders: 0`. The alerts are
   a side effect of rebuilding the feature panel, not order intents.

   The bug is in the reporting, not the behaviour: an alert stream that says
   `auto_trade: true` next to a flush that will never act on it makes "correctly
   did nothing" and "silently dropped three entries" look identical from the
   log. **The alert should carry the run mode**, so a flush-only pass is
   self-evidently not an order path.

   and 9.3m with one, the single best result (2.4m) came *during* stage 1, and
   the worst quiet-CPU result was 15.9m. n=9, no relationship.

   **Instrumentation added** (`core/API/Alpaca_API/runners/decision_latency.py`,
   writing `decision-latency.jsonl` into each live-SPY run directory). The
   leading hypothesis it is built to test: a 10-minute bucket only closes when
   the **first bar of the next bucket arrives**
   ([live_runner.py:169](core/API/Alpaca_API/runners/live_runner.py#L169)), so
   any gap in the 1-minute IEX stream defers the close by exactly that gap —
   no compute involved. Each record carries `close_detection_lag_sec`,
   `handler_queue_sec`, per-stage `inference` / `order_policy` seconds, and
   `bars_in_bucket` vs `expected_bars_in_bucket` (a short count is the
   signature of a sparse feed). Read it with
   `scripts/analyze_spy_decision_latency.py`, which attributes the lag and says
   which stage dominates.

   Why it matters even though every action today was flat: the 10-minute model
   only produces the setup probability. Entries are confirmed on 1-minute bars
   inside a window bounded by `meta_intrabar_setup_max_bars 3` and
   `meta_intrabar_max_confirmation_age_minutes 30`. A setup delivered 20 minutes
   after its bar closed opens that window over price action that has already
   happened.

9. **`on_decision`'s own entry path cannot authorize an entry, by construction.**
   `_new_entries_allowed` refuses when `now - local_ts > max_live_entry_lag_sec`
   (180s), and in `on_decision` `local_ts` is the 10-minute bar's *start*
   timestamp ([order_policy.py:4215](strategies/spy_intraday/Policy/order_policy.py#L4215)).
   Even a decision computed the instant the bar closed is already 600s past that
   timestamp, so the check at
   [order_policy.py:4310](strategies/spy_intraday/Policy/order_policy.py#L4310)
   always fails. Live entries evidently arrive through the 1-minute path
   (`on_1m_bar` → `_target_contracts_for_side`), where `local_ts` is the
   1-minute bar and the guard is meaningful — that is consistent with the 8
   round trips on 2026-07-29. Flagged as latent, not confirmed harmful: if the
   10m path is *intended* to be entry-capable, the guard is comparing against
   the wrong timestamp.

9. **xgboost artifact-version warning** on both launches (00:38:29, 09:01:55):
